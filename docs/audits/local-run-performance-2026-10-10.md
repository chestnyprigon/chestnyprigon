## Причины низкого выхода

1165 записей имеют options_confirmed_empty и пропущенные последующие отчёты. API /options/choice возвращает выборочные опции: пустой ответ не доказывает отсутствие стандартного оборудования. Старый scripts/encar/enrich.ts использует fallback equipmentOptionsFromCodes из detail.options.standard. Новый radar worker изолирует запись сразу и не запрашивает отчёты; publication-gate допускает для options только ok. Кроме того, endpoint-outcomes.ts переводит options HTTP404 в confirmed_empty, объединяя отсутствие endpoint и пустой успешный ответ. Это требует изменения семантики, а не ослабления проверки ID. Наличие пригодного standard у всех 1165 не установлено; обещать их публикацию нельзя.

## Причины длительности

CATALOG_POLICY.requestDelayMs=10000; паузы стоят между options, inspection, diagnosis, insurance, history availability/history и между карточками. Полная карточка получает около 50–70 секунд только ожиданий, сверх сети/БД/повторов. Исторический локальный отчёт описывает batch10 и паузу7 секунд между карточками; точное время старого запуска не подтверждено.

В режиме контроллера каждый автомобиль запускает отдельный npm/tsx процесс; standalone --until-complete обрабатывает10 в одном дочернем процессе. После каждой волны screenCompletedItems повторно читает и последовательно upsert всех накопленных результатов run. При последовательности волн объём повторной работы растёт; размер волны не равен параллелизму запросов.

## Изменения для следующего запуска, в порядке исполнения

1. Разделить пустые дополнительные опции, стандартное оборудование, HTTP404 и техническую ошибку. Проверить сохранённые payload; использовать подтверждённые стандартные коды с provenance. Изменить worker и общий publication-gate согласованно. Пропущенные отчёты не выдавать за отсутствие отчётов.
2. Унифицировать предварительный отбор с основной политикой: только критерии, доступные в search. Затем один detail, сверка advertised/canonical IDs и всех доступных identifiers, ранняя дедупликация, предварительный screening; дополнительные endpoint только прошедшим. Не исключать по неподтверждённым данным.
3. Сделать screening инкрементальным по новым/изменённым payload, с агрегированным отчётом run и одной полной итоговой сверкой; сохранить проверку каждой карточки до публикации.
4. Убрать создание процесса на каждую карточку: последовательный worker с проверкой pause/stop и lock между карточками. Размер отчётной волны адаптивный, независимый от темпа Encar.
5. Сохранить единый ограничитель запросов и остановку при CAPTCHA/403/429. Интервал менять только по измерениям безопасного малого пилота; сокращение повторной работы не требует ускорения запросов Encar.
6. Перед большим запуском измерить этапы, число запросов, время ожиданий/БД, ранние отказы, canonical дубли, ошибочные изоляции, финальную конверсию. Отдельно сравнивать кандидатов, полное обогащение, screening-ready и реальные публикации.

Разбор не возобновляет текущую очередь и не изменяет правила публикации.
