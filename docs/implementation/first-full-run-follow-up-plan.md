# План улучшения полуавтоматических прогонов каталога

Зафиксировано: 2026-10-16. План согласован владельцем. Реализация выполняется по этапам с отчётом после каждого этапа.

## Цель

Обрабатывать полный набор кандидатов на Mac mini через домашнюю сеть. Состав и прогресс каждой волны сохраняются отдельно. Пока worker обогащает следующие волны, завершённые волны можно независимо скринировать и готовить к публикации. Публикация остаётся отдельным действием с явным разрешением владельца.

Следующий прогон планируется **без прокси**, напрямую из домашней сети Mac mini, чтобы наблюдать реальные ответы Encar на принятой безопасной скорости. Это требование к будущей конфигурации; фиксация плана и разработка сами по себе не запускают Encar-запросы или прогон.

## Принятые решения

- Число и размер логических волн рассчитываются из фактического числа кандидатов данного прогона. Волны по возможности равные; состав каждой волны фиксируется до начала обработки и далее не меняется.
- Внутренний размер технической пачки и параллельность запросов — отдельные настройки. Они не меняют состав логических волн.
- Каждое объявление закреплено за run и wave ID и имеет сохраняемую историю состояний, попыток и результата. Очередь следующей волны не включает уже закреплённые записи.
- После завершения обогащения волны её screening и подготовка неизменяемого списка публикации не блокируют обработку последующих волн.
- Квоты марок служат для равномерного распределения поиска и предотвращения перекоса по популярным маркам. Они не являются самостоятельной причиной отказа карточке, которая соответствует критериям каталога.
- Единичные и некритичные технические ошибки получают ограниченные повторы, после чего запись классифицируется и очередь продолжается. Весь worker останавливается только при системном/безопасностном условии: подтверждённое ограничение источника, массовая недоступность сети/прокси (если он будет использоваться), ошибка авторизации или нарушение целостности, требующее остановки.
- Отсутствие необязательного отчёта, отказ по бизнес-правилу, изоляция из-за противоречия и техническая ошибка — отдельные исходы с отдельными причинами.
- Скрининг и публикация не меняют очередь обогащения. Для каждой публикационной партии сохраняются точный манифест, версия screening, причины допуска и результат по каждой карточке. Публикация возобновляема и защищена от дублей.
- Telegram показывает текущий run и wave, обработанные/ожидающие записи, результаты и конкретные причины. Длинные JSON и сырые сообщения ошибок заменяются читаемой сводкой; подробности доступны отдельным отчётом.
- После исчерпания очереди run автоматически получает конечный статус; retriable запись не должна оставлять его бесконечно активным.

## Этапы и критерии завершения

### 1. Зафиксировать спецификацию и обследовать текущую реализацию

Составить карту run/wave/queue/screening/publication/Telegram/Mac worker, определить текущие таблицы, функции и блокировки. Проверить сохранение состава очереди, точность состояний, обработку lease/retry, возможность независимого screening и публикации. Снять read-only исходные счётчики; не трогать production-данные.

**Готово:** документированы текущая схема, конкретные пробелы и изменения; отдельно подтверждено, что будущий режим direct не читает/не требует proxy credential.

**Результат аудита локального кода (2026-10-16):**

- `chestny_enrichment_runs` хранит общий запуск, `chestny_enrichment_queue` — кандидатов с уникальностью `(run_id, source_listing_id)`. Отдельной таблицы волн и ссылки queue item → wave нет.
- `run-local-enrichment-loop.ts` ограничивает один вызов `--max-items` (обычно 50), считает волну как разницу общих счётчиков. Этот размер не является сохранённым составом; после нового запуска граница определяется текущим прогрессом.
- Локальный launcher сохраняет run ID и числовой лимит в файлах состояния, но не список ID волны. Worker вызывает enrichment child с `CHESTNY_ENRICHMENT_DIRECT=false`, читает proxy credential из Keychain и всегда сообщает `decodo_proxy`.
- Нижележащий `run-vps-enrichment.ts` уже имеет direct transport: при `CHESTNY_ENRICHMENT_DIRECT=true` он использует native HTTPS, иначе требует proxy URL. Но local loop и preflight не дают безопасно выбрать direct режим; preflight сейчас только proxy.
- Локальный цикл запускает screening после обработки лимита, под тем же worker lock. При исчерпании всей очереди запускается `--full`; поэтому долгий скрининг блокировал новый Encar enrichment.
- Enrichment умеет сохранять retry metadata и повторно ставить ограниченные технические ошибки в очередь. Operational circuit breaker существует в нижнем worker. При этом local loop превращает ошибку child в паузу всего run; exhausted retries и конечный статус должны быть согласованы и проверяемы до закрытия очереди.
- Скрининг сохраняет машинные `decision`, `rules_version`, `evidence` и причины; детали доступны в коде результата, но Telegram показывает преимущественно общие счётчики и не предоставляет компактную разбивку точных причин.
- Публикационные cohort manifests уже существуют и защищают от части дублей. Публикация крупного списка блоками дала безопасный способ восстановления, который нужно оформить как штатное сохранённое состояние партии.
- Поиск уже исключает известные source IDs глобально и сохраняет offset для отдельных поисковых направлений. Брендовые квоты используются для распределения поиска; бизнес-решение о допуске задаётся screening, а марка сама по себе не должна становиться отказом.

Исходные таблицы и текущие RPC просмотрены в миграциях репозитория. Удалённая схема/production счётчики этим аудитом не запрашивались и не менялись.

### 2. Явная модель run и равномерных волн

Рассчитывать план волн из количества выбранных кандидатов и выбранного безопасного числа волн/ограничений политики. Сохранять план и точный состав до обработки. Повторное выполнение использует сохранённый wave ID и не пересчитывает границы. Новые кандидаты добавляются новым run/явно новой волной.

**Готово:** для короткого, делящегося и неделящегося объёма тесты подтверждают равномерность, отсутствие пересечений и полное покрытие; перезапуск восстанавливает исходный план.

### 3. Точные состояния и причины исхода

Задать справочник конечных результатов и машинных `reason_code`: успешно обогащено, источник недоступен/объявление снято, отклонено конкретным правилом, изолировано по целостности, техническая ошибка после повторов, ожидает повтора, допущено скринингом, опубликовано. Хранить этап, endpoint, HTTP-статус, попытку, дату и безопасное пояснение там, где применимо.

**Готово:** каждое задание имеет один однозначный исход; отчёт не смешивает «не подходит», «данные отсутствуют» и «не удалось получить».

### 4. Надёжное продолжение очереди и политика ошибок

Исправить повторную постановку временных ошибок, lease recovery и завершение run. Ограничить повторы и задержки. Некритичная ошибка отдельной карточки после лимита попыток фиксируется и пропускается; массовые/опасные ошибки открывают circuit breaker и останавливают запросы к Encar с понятным сообщением владельцу.

**Готово:** единичная сетевая ошибка не останавливает очередь; подтверждённый 403/429/CAPTCHA не вызывает дальнейший поток запросов; исчерпанная очередь не остаётся в `running`.

### 5. Независимый скрининг завершённых волн

Запускать screening по завершённой волне, пока enrichment worker продолжает следующую. Screening использует точный wave manifest, идемпотентен и не занимает глобальную блокировку Encar. Результат включает причины допуска, отказа и изоляции.

**Готово:** длительный screening одной волны не блокирует Encar worker; повторный screening обновляет результат без дублирования/потери состава.

### 6. Манифесты и возобновляемая публикация

Формировать отдельный неизменяемый манифест на выбранную волну/партию. Проверять дубли каталога и соответствие ID до публикации. Публиковать безопасными блоками с сохранением результата для каждого ID; продолжать после сбоя с первого незавершённого элемента. Не публиковать без отдельного разрешения владельца.

**Готово:** повторный запуск не дублирует опубликованные карточки; точная сверка показывает соответствие манифеста и публичных записей.

### 7. Telegram и управление Mac mini

Показывать состояние run и волн без устаревших значений и JSON. Уведомлять о завершении каждой волны и готовности screening/манифеста. Команды паузы, продолжения и остановки должны иметь однозначное действие. Добавить preflight для выбранного транспорта (`direct` или `proxy`) и показывать его до запуска без секретов.

**Готово:** Telegram отражает сохранённое состояние; worker после перезапуска восстанавливается; direct preflight явно подтверждает отсутствие proxy dispatcher/credential и не делает Encar-запросов.

### 8. Безопасная проверка и ввод в работу

Проверить расчёт волн, возобновление, независимую обработку стадий, причины ошибок, дубли и остановку circuit breaker на тестовых данных. Отдельно выполнить сетевой тест direct только после согласования конкретного тестового запроса; сам массовый прогон запускать только по отдельному разрешению владельца.

**Готово:** все критерии предыдущих этапов выполнены, результаты и ограничения отчитаны; перед массовым запуском владелец видит готовую конфигурацию и точный объём.

## Опыт первого полного цикла, который должен быть учтён

- Очередь успешно обработала 3 804 кандидата, но 42 ошибки и одна запись с доступным повтором оставили worker в неопределённом/долго живущем состоянии. Нужны точная политика retry и автоматическое конечное состояние.
- Run, волна и общий прогресс в некоторых уведомлениях расходились. Источником статуса должна быть единая сохранённая модель с явной связью wave → run.
- Большой полный screening конфликтовал с обработчиком очереди и блокировал общий lock. Стадии нужно развязать.
- Большая публикационная операция столкнулась с таймаутом; разделение на блоки по 50 прошло успешно. Публикационный манифест и прогресс блоков должны сохраняться и возобновляться.
- Подготовка более позднего диапазона обнаружила уже импортированные карточки. Отбор партий должен исключать публикации из предыдущих manifest/run и сверять реальные каталожные связи, а не только порядковый диапазон.
- Итог публикации удалось подтвердить отдельной сверкой по источникам, vehicle IDs и `is_public`; такая reconciliation должна стать штатным шагом.
