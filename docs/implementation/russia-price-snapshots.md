# Сохранённые расчёты для каталога РФ

## Модель хранения

`public.russia_price_snapshots` хранит один текущий снимок на активное объявление, источник и назначение. История пересчётов не создаётся. Снимок содержит результат TKS и коммерческий расчёт в одном JSON-объекте, отдельный `power_resolution` с версией и SHA-256 отпечатком значимых параметров автомобиля, статус и даты. Так источник-результат мощности сохраняется в базе и используется повторно, пока не изменились модель, двигатель, топливо, привод или исходная мощность. Для временной оценки после сбоя резолвера срок кэша — 7 дней; исходный проверенный PowerRecord хранится до изменения параметров или версии кэша.

Таблица закрыта для `anon` и `authenticated`; серверный сайт и фоновая задача читают/пишут её через service role. Триггеры ставят строку в очередь при публикации, снятии с публикации или изменении входных полей. При снятии объявления снимок удаляется. Счётчик `revision` защищает от сохранения расчёта, если данные объявления изменились во время вызова внешнего API.

## Фоновый пересчёт

Команда: `npm run pricing:refresh-russia`.

По умолчанию за один запуск обрабатывается до 100 строк с параллельностью 4. Фоновая задача берёт только новые/изменённые объявления (`pending`) и ошибки, для которых наступил срок повтора; готовые снимки больше не пересчитываются по расписанию. После успеха следующая автоматическая дата устанавливается далеко в будущем, а новый расчёт запускается при изменении значимых полей объявления либо по явному действию пользователя «Обновить цену». При повторном расчёте сохранённая мощность используется без запроса resolve; резолвер вызывается только если нет подходящего результата, изменились power-поля или истёк срок временной оценки. Ошибка повторяется через 30 минут, ограничение API — через 60 минут. Настройки можно менять через `RUSSIA_PRICE_BATCH_SIZE` (1–100) и `RUSSIA_PRICE_CONCURRENCY` (1–4). stdout содержит только агрегированные счётчики и коды ошибок.

У уже готовых снимков новая колонка изначально останется пустой: автоматический массовый повторный расчёт всей базы отключён. Мощность будет записана при следующем целевом обновлении объявления или явном обновлении цены; чтение страницы не запускает backfill.

Для однократного заполнения старых снимков доступна команда `npm run pricing:backfill-russia-power -- --apply`. Она переносит уже сохранённую мощность из расчётов в `power_resolution`, сверяет текущие входные данные объявления и `revision`, не пересчитывает цену и не вызывает Vehicle Power/TKS. Без `--apply` команда работает как dry-run и выводит только число подходящих строк.

Systemd примеры: `ops/russia-price-refresh.service.example`, `ops/russia-price-refresh.timer.example`, `ops/russia-price-refresh.env.example`. Таймер запускает задачу каждые пять минут; systemd не запускает второй экземпляр того же oneshot-сервиса, пока первый ещё работает. На Mac mini LaunchAgent-loop берёт следующую партию через две минуты после завершения предыдущей.

## Безопасный rollout

1. Создать миграцию для price snapshots в Supabase после проверки SQL на staging/копии базы.
2. Установить на worker-хост новые server-only секреты `VEHICLE_POWER_RESOLVE_TOKEN` и `VEHICLE_POWER_TKS_TOKEN`, а также Supabase service-role. Значения не помещать в репозиторий или журналы.
3. Сначала применить миграцию для `power_resolution`, затем развернуть worker и сайт.
4. Новые и изменённые объявления рассчитываются worker-ом. Уже готовые снимки не попадают в массовый повторный backfill; страницы каталога только читают БД и не вызывают Vehicle Power/TKS при отсутствии снимка (в UI отображается «Расчёт уточняется»).
5. При явном обновлении цены API повторно использует сохранённую мощность и сохраняет обновлённые цену и provenance.

Миграция и worker подготовлены локально. Применение миграции и production deployment требуют отдельного rollout на целевом окружении; этот документ сам по себе не выполняет эти действия.
