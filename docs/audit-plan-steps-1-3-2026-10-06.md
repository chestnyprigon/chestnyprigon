## 2. Связность данных — выполнено частично

| Требование | Подтверждение и пробел |

| Цепочка ID | Worker проверяет URL `carid`, snapshot, очередь, canonical ID, существующий staging/catalog и source identifiers. Проверяются ID inspection и diagnosis. Перед публикацией эти проверки повторно не вызываются: `publish-vps-staging` восстанавливает `search.Id` из staging и сравнивает normalizer canonical ID с тем же `detail.vehicleId`. Это не независимая проверка связности. |
| Снапшот и основные характеристики | Worker сравнивает марку, сопоставимую модель, явно переданный модельный год, топливо, коробку и объём; дрейф цены и пробега сохраняет как предупреждение и использует свежие detail-значения. | Автоизоляция и точная причина | Конфликты worker блокируют дальнейшее обогащение и сохраняют код, ожидаемые/фактические значения и источник. Но исход очереди — `failed`, `failureClass=identity_integrity`, `retryable=false`; единого screening `isolated` для таких записей не создаётся. |

Локальное воспроизведение без записей: `screenListing` возвращает `approved` для bundle с подменёнными detail ID/маркой/моделью и для фотографий другого ID; `classifyEndpointProbe` для insurance с ожидаемым ID `123`, payload `vehicleId=999, openData=true` возвращает `ok`. Это не означает, что worker пропускает любую подмену: там есть дополнительные проверки. Это показывает, что screening и публикационный путь сами эту гарантию не обеспечивают.

### 2. Связность данных

- До запроса проверяется очередь, Encar URL, snapshot и соответствие ID. После получения сверяются canonical ID, ID supplemental endpoints и госномер отчёта, если он есть; источник, фотографии, staging и сохранённые поля карточки проверяются повторным publication gate.
