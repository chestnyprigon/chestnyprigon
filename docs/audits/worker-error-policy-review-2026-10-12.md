# Проверка настройки worker и причин остановок — 12 октября 2026

Проверены установленный код Mac mini, журнал worker, сохранённые результаты
run `26013f2d-c123-430b-987b-d3d370f40899` и исторический код VPS worker.
Encar-запросов, запуска очереди и изменений runtime в ходе проверки не было.

## Фактические параметры

- Последние семь пачек журнала: `transport=decodo_proxy`, задержка 10 000 мс,
  одна машина одновременно, получение очереди по 10 записей.
- Обёртка явно передаёт дочернему worker `CHESTNY_ENRICHMENT_DIRECT=false`
  и `ENCAR_PROXY_URL`, прочитанный из Keychain. Дочерний worker создаёт
  `ProxyAgent` и передаёт его как `dispatcher`.
- Задержка действует между дополнительными endpoint и между машинами.
  Для машины с доступной историей выполняется семь API-запросов и примерно
  семь пауз по 10 секунд, помимо сетевого времени и повторов.
- Обычный run не позволяет снизить задержку ниже 10 секунд. Это существующая
  настройка безопасного темпа, а не причина сетевых ошибок.
- Максимум короткого цикла — три попытки запроса, timeout — 25 секунд.
- В режиме `untilComplete` ограничение одной итерации — 5 000 обработок,
  а не 50. На этот run из 1 256 записей лимит не влиял.
- Восемь проверенных файлов политики/транспорта совпадают между машинами.
  Обёртка отличается только пустой строкой; поведение одинаково.

У 42 успешных записей решение gate — 37 `approved`, 5 `rejected`
(один lease, четыре исключённых типа использования по осмотру).
Это сохранённые решения отбора, а не утверждение о выполненной публикации.
У 35 успешно обработанных записей дополнительные опции вернулись пустым
массивом; подтверждённое стандартное оборудование позволяет продолжить.
Диагностика вернула 404 у восьми записей; подтверждённое отсутствие
необязательного отчёта также допускается.

Последняя пачка резервировала 10 записей. Обработаны восемь: одна успешно,
два конфликта ID, пять сетевых ошибок (четыре detail `fetch failed`, одна
`diagnosis_transient_error`). Две оставшиеся записи возвращены в очередь.
Пять технических ошибок запустили остановку. В сохранённых результатах
этой пачки нет 403/429 или CAPTCHA; сообщение не доказывает блокировку Encar.
Причина `fetch failed` сохранена без низкоуровневого `cause`, поэтому точный
источник сетевых сбоев — proxy, TLS, соединение или upstream — не установлен.

## Подтверждённые недоработки

1. **Повторы исчерпываются слишком рано для длительного прогона.** После
   короткого цикла с тремя попытками выставляются `retryExhausted=true`
   и `retryable=false`. Возврат в очередь явно исключает такие записи.
   Отложенного повторного цикла после восстановления сети нет.

2. **Пустой detail ошибочно получает постоянную категорию integrity.**
   Ответ `[]` обрабатывается вместе с неоднозначным ответом из нескольких
   машин: `identity_detail_response_cardinality`, `retryable=false`.
   Нужны отдельная проверка доступности и ограниченный повтор для пустого
   ответа; несколько противоречивых машин должны оставаться изолированными.

3. **Пауза управляется в двух местах.** Дочерний worker останавливается
   после пяти ошибок за пачку, обёртка — после пяти ошибок в последних
   десяти обработках. В обоих случаях учитываются все `failed`, кроме
   `identity_integrity`, включая ошибки формата отдельных карточек.
   На текущем размере пачки 10 условия близки; при пачке 50 внутренние
   пять ошибок могут остановить run при существенно меньшей доле сбоев.
   Нет общей политики охлаждения, ограниченного восстановления и единого
   различения системного сбоя и проблем конкретного объявления.

4. **Причина паузы сохраняется неполно.** Дочерний worker записывает только
   `lastResult`. После изменения статуса на `paused` обёртка пытается
   записать понятную причину только для `approved/running/completed`,
   поэтому обновление уже приостановленного run ничего не меняет.
   В БД теряется объяснение порога; в Telegram появляется общая формулировка.

5. **HTTP 407 классифицируется неодинаково.** Для detail это `auth_error`,
   для дополнительных endpoint — `http_error` и изоляция. Это воспроизведено
   чистой функцией `classifyEndpointProbe`, без сети. Статус нужно сохранять
   вместе с endpoint и контекстом маршрута, чтобы отличать ошибку доступа/
   авторизации от содержимого карточки. Сам по себе 407 в старом прямом
   запуске не доказывает неверные реквизиты нового proxy.

6. **Частичное обогащение не сохраняется при ошибке.** В ветке catch передаётся
   `p_payload=null`; при сбое diagnosis/insurance уже полученные detail,
   галерея и успешные дополнительные блоки не становятся checkpoint.
   Следующая обработка вновь получает эти блоки. Ошибка карточки не означает
   её непригодность, но текущая модель не хранит пригодные частичные результаты.

Проверки реальных ID и связей, требования к галерее/характеристикам, исключение
lease/rental/taxi и разделение подтверждённого отсутствия отчёта от технического
сбоя следует сохранить. Они не объясняют последнюю сетевую остановку.

## Отличия от прежней схемы

Исторический Chestny worker на `f759a42` запрашивал четыре дополнительных
endpoint параллельно, выдерживал паузу между машинами и преобразовывал
ошибку отдельного дополнительного API в `null`, сохраняя карточку как
`succeeded`. Поэтому высокий счётчик успешного обогащения не подтверждает
полноту всех дополнительных данных или факт публикации. Точный эффективный
серверный commit и env конкретного исторического прогона по-прежнему не доказаны.

Текущий worker проверяет связи ID, предварительно отсеивает неподходящие
машины и последовательно запрашивает дополнительные блоки. Эта часть
согласованной схемы присутствует. Основные проблемы находятся в обработке
ошибок, повторов и пауз, а не в отсутствии предварительного screening.

## Что исправить перед новым discovery/enrichment

1. Разделить `duplicate/identity_conflict`, `source_unavailable`,
   `retry_pending`, некорректные данные отдельной карточки и системный сбой.
2. Добавить сохранение частичных результатов и ограниченные отложенные
   повторы временных ошибок с продолжением недостающих блоков.
3. Оставить одного владельца политики остановки: подтверждённое ограничение
   доступа — отдельная пауза; серия временных сбоев — охлаждение и ограниченная
   попытка восстановления; одиночные проблемы карточек не останавливают очередь.
4. Сохранять структурированную причину паузы и низкоуровневую сетевую причину
   без секретов; показывать её понятным сообщением в Telegram.
5. Проверить сценарии без сети, затем отдельную согласованную малую проверку
   через Mac mini и proxy. Скорость и критерии публикации автоматически не менять.

## Дополнительное подтверждение с VPS

Присланный владельцем вывод `git` и `systemctl show` подтверждает текущий
checkout VPS `07156f6` и загрузку enrichment-сервисом файлов
`/home/ubuntu/tl-auto/.env`, затем `.env.enrichment` проекта Chestny.
Отсутствие обычного `.env` Chestny не означает отсутствия proxy у сервиса.
Последний EnvironmentFile может переопределить значения предыдущего.
Это текущая конфигурация, а не доказательство SHA/окружения исторического запуска.

Сравнение `git diff f759a42 07156f6 -- scripts/radar/run-vps-enrichment.ts`
пустое: описанный выше старый алгоритм совпадает с worker текущего VPS checkout.
Его default — batch 50, пауза между машинами 4 секунды, максимум 3 попытки;
эффективные переопределения из окружения присланный вывод не раскрывает.
Название коммита про monitor batch 1000 не меняет лимит enrichment batch 50.

Эффективный ExecStart enrichment последовательно вызывает worker для трёх
run ID; каждый вызов забирает одну партию. Конструкция `|| echo` поглощает
ошибку вызова и продолжает следующий run. Без сведений о Restart/timer нельзя
считать этот unit самостоятельным циклом до полного опустошения очередей.
Общий `flock` сериализует enrichment и report-retry на этом VPS, но не процессы
других хостов.

Повторяющийся report-retry `requested: 0` означает ноль обработанных карточек,
а не успешный сетевой тест. Код допускает это при пустом claim либо уступке
приоритета Radar до первой карточки. Поэтому этот журнал не подтверждает
работоспособность запросов к Encar или отсутствие ограничений.

## Исправления, установленные 12 октября

На Mac mini установлены изменения четырёх файлов worker/policy/endpoint classifier;
оригиналы сохранены в `output/worker-policy-fix-20261012/*.ts.bak`.

- HTTP 407 дополнительных endpoint классифицируется как ошибка доступа,
  а не окончательный дефект данных карточки.
- Пустой detail-массив отделён от нескольких неоднозначных detail-объектов:
  пустой ответ допускает ограниченный повтор; неоднозначные ID изолируются.
- Короткие endpoint-повторы и повторная обработка карточки разделены.
  Временная ошибка сохраняет retry_pending/retryAfter; максимум три обработки
  карточки, интервал перед повтором пять минут. Run не завершается, пока
  остаются эти отложенные повторы. Старые retryExhausted записи автоматически
  не реабилитируются; отменённые run не возобновляются.
- Detail/галерея и результаты каждого дополнительного endpoint сохраняются
  в JSON результата очереди, не в опубликованном каталоге. При повторе detail
  и проверки связей выполняются заново. Повторное использование успешных
  блоков ограничено 30 минутами и совпадением canonical ID и номера автомобиля.
- Локальный контроллер владеет окном сетевых ошибок между партиями; внутренний
  worker не применяет прежний независимый порог пяти любых ошибок. Ошибки
  галереи/данных/ID не считаются транспортной аварией. После первой серии
  временных сбоев контроллер ждёт пять минут и делает одну попытку продолжения;
  повторная серия требует внимания. Ограничение доступа останавливает сразу.
- В причине паузы присутствуют source/message; при сетевой ошибке сохраняются
  безопасные code/name вложенной причины без URL и credentials.

Локальная и целевая Mac mini проверки TypeScript прошли. Сетевые тесты,
Encar-запросы и прогоны не выполнялись. Работоспособность на реальном источнике
предстоит проверить отдельным разрешённым малым запуском. SQL не требуется.
