1. Применить миграцию `20260916_universal_encar_enrichment_queue.sql` в Supabase TL Auto.
2. Найти фактический read-only файл со списком 2 290 карточек и проверить: количество, уникальность `source_listing_id`, отсутствие уже обработанных/активных дублей.
3. Создать run со статусом `awaiting_approval` через `prepare:encar:enrichment`; Encar-запросов и публикации эта команда не делает.
4. Выполнить dry-run первой партии 50 через VPS и существующий прокси. Замерить active/404/error и фактический объём response-body в байтах/МиБ/ГиБ.
5. После проверки конфигурации перевести run в approved и включить общий worker.
6. Worker работает последовательно, партиями, с паузой, общим `flock` и механизмом lease/retry. Если занята приоритетная очередь Radar — обогащение ждёт; Radar не блокируется.
7. После завершения всех волн сделать локальный read-only screening уже сохранённых staging-данных. Локальные запросы к Encar не выполнять.
8. Только после отчёта и проверки — подготовить отдельную очередь публикации и тестовую публикацию небольшой партии.

## Действующие процессы и важные ограничения

На VPS Radar имеет приоритет: `autoexport-radar-worker.service`, fast/audit timers. Также работают актуализация каталогов и существующий TL Auto enrichment-контур. Новую универсальную службу нельзя смешивать с Chestny-очередью или менять существующие unit-файлы без отдельной проверки.

Использовать:

- один текущий проверенный прокси;
- один последовательный поток массового Encar-обогащения;
- общий lock/координацию с Radar;
- небольшие волны (ориентир 50) и паузу около 3 секунд, затем корректировать только по метрикам;
- остановку при CAPTCHA, 403/429, резком росте `fetch failed`, timeout или proxy errors.

Не делать:

- не запускать локальный Encar-fetch;
- не запускать параллельно ручной worker и systemd worker;
- не использовать второй прокси для обхода блокировок без отдельного согласования;
- не менять production-карточки на этапе VPS;
- не публиковать `succeeded` автоматически без screening.

## Цель

Увеличить текущий каталог на 1 000 новых опубликованных объявлений. Публикация считается успешной только после сохранения карточки, прохождения скрининга и отдельной сверки итогового количества.

## Текущий этап

Сначала выполняется локальный read-only отбор кандидатов из общей базы Radar/Supabase. На этом этапе не запускается VPS, прокси и массовая публикация. Результат отбора сохраняется в `output/radar-local-candidates.json`.

Для предыдущего локального пула из 3 050 кандидатов после обогащения было 1 172 активные карточки: 989 опубликованы и 183 скрыты. Эти цифры являются контрольной точкой предыдущего пула, а не гарантией итогового состояния всего каталога.

## Правила проекта

- Минимальный год выпуска: 2016 включительно.
- Допустимый пробег: не более 190 000 км.
- Допускаются обычные продажи; аренда, лизинг, такси, коммерческий и специальный транспорт исключаются.
- Электромобили и водородные автомобили исключаются; гибриды допускаются.
- Нужны корректные идентификатор, цена, модель и изображения.
- Аварии не являются автоматическим запретом: они раскрываются в карточке количеством страховых случаев и выплатами.
- При `reportStatus=unavailable` карточка может быть опубликована, если остальные правила пройдены; отображается компактная отметка «Нет данных по страховым случаям».
- Дубли и уже существующие `source_listing_id` не добавляются.
- Удалённые объявления не публикуются и не повторяются в следующем запуске.
- Порог свежести для новых кандидатов — до 180 дней; более старые активные объявления допускаются только после отдельного согласования.

## План безопасного запуска через VPS

1. Локально сформировать резерв 1 200–1 300 кандидатов, чтобы компенсировать отказы и недоступные отчёты.
2. На VPS использовать один разрешённый прокси и один последовательный поток запросов.
3. Обрабатывать партии по 50–100 карточек с паузой 3–8 секунд между запросами.
4. После каждой партии сохранять сырые данные, отчёт обогащения и решение скрининга в Supabase; публикацию делать только после сверки партии.
5. После каждых 200–300 карточек считать: fetched, missing/404, report ready, report unavailable, approved, rejected, published, hidden.
6. Остановить запуск при CAPTCHA, 403/429, резком росте ошибок, несоответствии идентификаторов или подозрительной смене ответов. Не обходить CAPTCHA и не применять ротацию IP для обхода ограничений.
7. После достижения 1 000 новых публикаций остановить дальнейшее обогащение.

## Правила публикации

Карточка публикуется только если она активна, не является дублем, прошла screening `approved`, имеет валидную цену и изображения. Отчёт Encar может быть `ready` или `unavailable` согласно правилу выше. Отклонённые и требующие ручного решения остаются скрытыми.

## Ограничения и безопасность

- Не использовать локальный и VPS-запуск одновременно.
- Не запускать параллельные массовые волны.
- Не считать кандидатов опубликованными до проверки базы.
- Не менять существующие опубликованные карточки без отдельной задачи актуализации.
- При повторном запуске использовать только ещё не обработанные или явно разрешённые к повторной проверке IDs.

### Исправление статусов после retry

После повторной проверки отчётов была обнаружена ошибка: generic RPC для полной карточки использовался и для report retry. Из-за этого `enrichment_status` мог стать `unavailable`, хотя detail payload и галерея уже были успешно сохранены.

Исправление данных уже выполнено:

- все **1 488** staging-строк с непустым `encar_payload` снова имеют `enrichment_status=succeeded`;
- только **118** строк без payload остаются `enrichment_status=unavailable`;
- исходный run `ebe8fa15-1732-4a0d-876f-b1a9a05556f7` переведён в `completed`;
- `report_status` при этом не менялся.

Перед следующим запуском report retry обязательно применить миграцию `20260917090000_chestny_report_retry_outcomes.sql`. Она создаёт отдельное безопасное завершение retry-очереди, сохраняет классификацию отчёта и запрещает retry-worker перетирать detail payload, галерею и статус обогащения карточки.

## Что было недоработано в прогоне

1. Статус `unavailable` слишком общий. Worker превращает в один результат отсутствие/невалидность inspection-ответа, HTTP-ошибку, timeout и техническую ошибку прокси. В коде ошибки inspection/summary подавляются через `catch(() => null)`, поэтому невозможно отличить «отчёта действительно нет» от «запрос не получил ответ».
2. В staging сохраняется только булево `inspectionAvailable`, но не сохраняются HTTP-код, тип ошибки, timeout, причина ответа и время каждой попытки.
3. Запрос summary и options выполняется, но их ошибки не классифицируются отдельно. Поэтому текущие 1 485 `unavailable` нельзя считать доказанным отсутствием страхового отчёта.
4. Завершённая очередь не перевела сам run в финальный статус: очередь пустая и все элементы терминальные, но `encar_enrichment_runs.status` остался `running`. Нужен отдельный безопасный finalize-шаг после сверки очереди.
5. В проекте остаются TypeScript-ошибки в `scripts/radar/run-vps-enrichment.ts` вокруг Supabase RPC-инференса (`never`). Это не вызвало сбой завершённого прогона, но должно быть исправлено до следующего production-запуска.
6. Локальный screening был выполнен корректно как read-only, но он работает по сохранённому staging и reconstructed snapshot. Он не должен подменять повторный запрос к Encar для выяснения причины недоступности отчёта.
