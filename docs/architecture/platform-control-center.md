# Целевая архитектура KoreDigital Control Center

**Статус документа:** архитектурный аудит исходного кода и целевой план изменений
**Дата аудита:** 2026-10-09
**Область:** автоматизация каталога «Честный пригон» на Mac mini и её дальнейшее развитие как общей платформы управления.

> **Обновление каталожного workflow (2026-10-23):** для новых запусков поиск охватывает все подходящие объявления до исчерпания источника; общий целевой объём и жёсткие квоты публикаций по маркам не задаются. Относительные веса брендов помогают сохранять разнообразие, но не ограничивают публикацию. Кандидаты сохраняются в сбалансированные, возобновляемые волны размером до 500; после screening каждой волны новый запуск автоматически публикует только записи, прошедшие все gates и сверку staging/очереди. Существующие runs сохраняют прежнюю политику. Пункты ниже — снимок аудита на 2026-10-09 и не описывают актуальный режим там, где ему противоречат.

## 1. Целевое устройство

Mac mini — постоянно работающий узел исполнения. Telegram — личная панель владельца для запуска задач, краткого статуса, прогресса и уведомлений. Источники, проекты и продукты подключаются к платформе как отдельные модули; они используют общие механизмы постановки задач, состояния, блокировок, журналирования, уведомлений и контроля доступа.

```text
Владелец
   │ Telegram: одна понятная панель
   ▼
Control Center (авторизация, команды, состояние, уведомления)
   │
   ├── Task coordinator: принимает цель, строит/проверяет план, ведёт этапы
   ├── Shared task state, event log, locks, schedules, health checks
   └── Capability modules
         ├── Chestny Prigon: Encar search → queue → enrichment → screening → publish
         ├── Другие продукты и источники (подключаются позднее)
         └── AI providers: только ограниченные интеллектуальные операции
   │
   ├── Supabase: каталог и долговременное состояние Chestny Prigon
   ├── Encar: только последовательные запросы локального worker
   └── Telegram: прогресс, отчёты и сигналы ошибок
```

На текущем этапе это целевая архитектура, а не описание уже готовой платформы. Репозиторий содержит автоматизированный каталоговый workflow и Telegram-команды, но не обнаружен общий координатор модулей или полноценный AI-агент, который самостоятельно планирует и ведёт цели. Не следует представлять систему как уже готовый KoreDigital Control Center.

## 3. Поток каталога, который уже реализован

1. Поиск читает квоты, остаток и сохранённый offset по маркам.
2. Запросы к Encar выполняются локальным поиском с паузой; найденные ID сравниваются с baseline, каталогом, source identifiers, raw, staging и очередью.
3. Уникальные кандидаты сохраняются в Supabase queue, а offset фиксируется вместе с результатом страницы через RPC.
4. Локальный launchd worker берёт run, ставит ограничения и блокировки, последовательно получает detail и дополнительные блоки Encar, сохраняет staging и endpoint outcomes.
5. Screening строит `approved`, `rejected` или `isolated` с кодами/доказательствами; временный технический сбой приводит к retry/pause, а подтверждённо отсутствующий необязательный отчёт допустим.
6. Отдельный publisher повторно проверяет staging, run, решение, квоту и дубли. Дополнительный DB trigger блокирует публикацию, не прошедшую проверку.
7. Telegram сообщает о статусе, прогрессе, результате волны и сбоях. Для новых запусков сохранённые правила могут включать публикацию после screening/gate каждой волны; старые runs не переключаются.

Это workflow с детерминированной автоматизацией. Координация целей и модульных задач пока завязана на конкретные команды и фиксированный каталоговый launch; автономного агента, которому можно поручить общую цель и который планирует этапы поверх разных модулей, в текущем коде нет.

## 4. Архитектурные изменения в порядке реализации

Изменения ниже — целевой список после пункта 1; они не считаются уже реализованными.

1. **Общий контракт задачи и событий.** Определить `goal/task/run/step`, статусы, идемпотентный event ID, прогресс, heartbeat, результат и error envelope. Сохранение событий не должно зависеть от Telegram.
2. **Control Center core.** Сервис на Mac mini читает команды/расписания, авторизует операции, управляет задачами через реестр разрешённых capabilities, выдаёт состояние и переживает рестарт без повторного запуска side effect.
3. **Product/source adapters.** Перенести каталожный search/enrich/screen/publish под один адаптер и закрепить интерфейс для будущих источников/продуктов. Доменная логика остаётся изолированной по модулю.
4. **Единый Telegram UX.** Один entry point: статус платформы и активная цель; кнопки «Найти и обработать следующую волну», «Пауза/Продолжить», «Остановить», «Отчёт». Кнопки вызывают ограниченные команды, опасные действия имеют run/goal-bound confirmation. Не выдавать внутренний список slash-команд как основной пользовательский интерфейс.
5. **Операционная наблюдаемость.** Сводки после волны и сразу при ошибке; health check для Mac/controller/worker/Supabase/Encar; ежедневный отчёт и системные метрики как отдельный этап. Каждый alert содержит этап, причину, влияние и разрешённое следующее действие.
6. **Права и секреты.** Telegram owner ID и private-chat boundary; отдельные права capability; сервисные ключи не доступны модели; запрет произвольного shell/SQL через Telegram или AI; Keychain/защищённый env; аудит управляющих действий и защита от replay.
7. **AI coordinator.** Только после пунктов 1–6. Принимает цель на естественном языке, формирует детерминированный исполняемый план из зарегистрированных действий, показывает план/лимиты и запрашивает подтверждение только для заранее определённых side effects. Не делает сам запросы/записи и не может менять бизнес-решение скрининга.
8. **Первый end-to-end pilot и затем масштабирование (исторический план).** Этот пункт описывал прежнюю ручную публикационную модель, фиксированную цель и квоты. Актуальные правила новых запусков приведены в обновлении от 2026-10-23 в начале документа.
9. **Масштабирование Control Center.** Подключать очередной продукт/источник через adapter contract; общий статус и наблюдаемость уже есть, а его credentials, данные и права остаются ограничены конкретным модулем.

## 5. Фактические границы и замечания аудита

- В нескольких пакетных утилитах/манифестах сохраняется историческая метка `vps` и старые VPS-скрипты. Локальная обёртка включает direct-транспорт явно; перед эксплуатацией необходимо следить, чтобы никакой команды VPS/proxy пути не попало в новый каталоговый workflow.
- Команда `/catalog_start` имеет два разных поведения: подготовленный run запускается без нового поиска; следующий поиск предлагается и запускается через inline confirmation только при завершённой/отменённой/приостановленной прошлой волне без queued/leased записей. Это верно описывать пользователю как выбор следующего цикла, а не как «бот сам непрерывно наполняет цель».
- Кнопки и slash-команды — команда-пульт, не автономный агент. Сейчас пользователь должен понимать, какую команду отправить для следующего действия. Это архитектурный и UX-разрыв с желаемой системой.
- Публикационный код использует service-role ключ, но список операций ограничен кодом worker/publisher; этот ключ нельзя передавать модели или превращать в произвольную команду.
- Для однозначной архитектуры несколько пересекающихся путей (legacy `pilot`, local reserve, VPS-labelled publisher, local worker) нужно свести к одному поддерживаемому локальному happy path и явно deprecated-списку старых entrypoint-ов.
- `docs/roadmap-local-ai-catalog.md` содержит исторические статусы тестов, миграций и развёртывания. Они не заменяют повторную проверку Mac mini, remote schema, Vercel deploy или реальный пилот; все эти факты помечены как ранее задокументированные, где они не проверялись в текущем аудите.

## 7. Общий контракт задач и модулей (пункт 2)

Реализован общий контракт в `scripts/control-center/contracts.ts`. Задача содержит `moduleId`, `product`, `source`, `goal`, `parameters`, `state`, `progress`, `result` и временные отметки. Состояния: `queued`, `preparing`, `ready`, `running`, `paused`, `completed`, `failed`, `cancelled`.

Единый интерфейс `ControlModule` требует `checkReadiness`, `run`, `pause`, `resume`, `stop`, `getStatus`. `ModuleRegistry` регистрирует адаптеры, маршрутизирует операции по `moduleId` и до вызова проверяет product/source/task agreement. `ControlTaskService` сохраняет переходы и итог задачи через общий repository; product-neutral persistence подготовлен миграцией `20261009010000_control_center_tasks.sql` в таблице `control_center_tasks`.

«Честный пригон» подключается первым через `createChestnyPrigonCatalogModule`: модуль `chestny-prigon.catalog`, продукт `chestny-prigon`, источник `encar`; registry принимает шесть одинаковых lifecycle операций через runtime ports. Следующий продукт подключается реализацией тех же операций и регистрацией в общем registry; общую модель задачи и управление повторно писать не нужно.

Миграция была подготовлена в пункте 2; 2026-10-09 владелец сообщил о её применении, read-only проверка подтвердила доступность таблицы и полей задачи. Worker controller теперь привязывает входящие команды к общей задаче, исполняет их через `ControlTaskService`/Chestny Prigon module и после обработки команд вызывает coordinator tick. Legacy command queue остаётся транспортом Telegram→Mac mini; она больше не является единственным форматом процесса. Telegram status endpoint показывает goal/state/stage/progress/result той же задачи. Перевод пользовательского интерфейса с технических команд на короткую панель остаётся отдельной работой.

## 8. Координатор автоматического выполнения (пункт 3)

`ControlTaskCoordinator` читает из Supabase незавершённые задачи, запрашивает у модуля следующий этап, сохраняет этап/action key до side effect, выполняет максимум один переход на задачу за tick и сохраняет результат. Следующий tick заново выводит действие из сохранённого состояния и фактического run; поэтому controller может продолжить после рестарта процесса или Mac mini без in-memory state. Одиночный launchd control loop уже запускается с интервалом 15 секунд и является хозяином ticks.

Chestny Prigon runtime связывает coordinator с текущими run/queue и launchd worker. Он запускает подготовленный run, автоматически продолжает только паузу `wave_limit`, следит за completed/paused/cancelled, пересчитывает число новых публикаций по брендовой квоте, запускает поиск следующей волны и вызывает publisher только при явных `pilotApproved=true` и `publishAuthorized=true`. Screen output передаётся publisher по пути конкретного run, а publisher для launch читает оставшиеся брендовые квоты из Supabase.

Новая цель создаётся в общем task store при первом подтверждённом Telegram start; задача содержит launch/run, цель 1 000, лимит волны 50 и отдельные закрытые флаги пилота/публикации. `/catalog_status` показывает её сохранённый этап и результат. Контроллер отправляет Telegram уведомление, когда сам выполняет следующий этап; worker продолжает отправлять отчёты волн и ошибки.

**Gate, следующий из уже утверждённого плана:** флаги `pilotApproved` и `publishAuthorized` создаются как `false`. Поэтому coordinator автоматически ведёт задачу до обработки и screening пилотной волны, затем сохраняет состояние `pilot_review` и ждёт владельца. После явного утверждения могут выполняться публикация и следующие волны; текущая работа не активирует эти флаги и не меняет production-данные.

### Добавлено локально 2026-10-09: автономный старт первой пилотной цели

`/catalog_start` теперь может показать одно подтверждение для создания отдельной пилотной цели при отсутствии run или при наличии старого `paused` run с остатком очереди. Цель сохраняется через идемпотентную RPC-функцию, имеет `external_ref = null`, флаги публикации выключены и стартует с этапа `search_pending`. На следующем Mac mini coordinator tick модуль запускает локальный resumable quota search, получает новый run, запускает worker и сохраняет его UUID в общей задаче. Поэтому `/catalog_status` может показывать этап до создания run.

Старый paused run остаётся на паузе с прежними элементами очереди. Поиск переключает брендовый search-progress на новый run только когда предыдущий run находится в `paused`; функция страницы поиска продолжает запрещать переключение от `approved`/`running` run и от очереди другого не-paused run. Уже известные ID исключаются общей проверкой поиска. Новая migration `20261009020000_control_center_initial_catalog_goal.sql` добавляет request-id дедупликацию для Telegram updates, защищённое создание цели и обновлённую checkpoint RPC. Это изменение пока только в локальном checkout: миграция не применена, webhook не развёрнут и Mac mini не обновлён.

## 10. Единый Telegram UX (пункт 4, статус: локальная реализация)

Webhook подготовлен к короткой постоянной клавиатуре с действиями «Статус», «Квоты», «Отчёт», «Следующая волна», «Продолжить очередь», «Пауза» и «Остановить». Командное меню бота сокращается до тех же диагностических и управляющих действий при `/start`; технические offsets остаются в отдельном отчёте квот.

Статус и подтверждения читают `pilotApproved`, `publishAuthorized` и `publicationMode` из сохранённой цели. Worker-сводка сообщает только screening-исход и наличие разрешения, а отдельное сообщение координатора фиксирует фактическое количество опубликованных карточек и ошибок после вызова пакетного publisher. Это устраняет прежнее неверное «публикация отключена/не выполнялась» для целей с разрешённой пакетной публикацией.

Локальная проверка: `npx tsc --noEmit`, ESLint по затронутым TypeScript-файлам и `git diff --check` проходят. **Пункт ещё не закрыт:** production webhook и Mac mini controller/worker должны быть обновлены с резервной копией; затем владелец проверит клавиатуру в Telegram и `/catalog_status`, а отчёт публикации проверяется на следующем безопасном завершённом этапе. Текущая цель каталога paused; worker не возобновлялся. Разбор правила автопаузы и конфликта ID остаётся отдельной последующей задачей по указанию владельца.
