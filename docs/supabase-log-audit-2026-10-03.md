# Анализ частых запросов Supabase, 3 октября 2026

## Дополнение, 4 октября

По предоставленному журналу VPS обнаружен Bash-цикл по трём завершённым run ID. Фактический таймер запускал его через `OnUnitInactiveSec=4min`; пользователь отключил только `chestny-enrichment.timer`. Это устраняет примерно 1 080 проверок статуса в сутки, но не объясняет весь объём логов. Развёртывание первоначального патча на VPS не подтверждено.

Pricing-таймер остаётся активным. Последний предоставленный журнал подтверждает успешный пересчёт 26 684 записей. В локальном `scripts/pricing/recalculate.ts` выявлена запись каждой записи отдельным PATCH вне зависимости от совпадения новой и сохранённой цены. При 24 запусках в сутки это 640 416 PATCH плюс запросы чтения; соответствие этому поведению кода VPS и доля в Log Ingestion требуют проверки.

Подготовлено локальное исправление pricing: чтение текущих `price_usd` и `krw_per_usd`, пересчёт всех автомобилей, запись только отличающихся результатов, ограничение параллельности также для ошибочных расчётов. Добавлен `--dry-run`, который читает данные и считает `wouldUpdate`/`unchanged`, не записывая их. Расписание и формула не изменены; существенное снижение зависит от количества реально неизменившихся строк. Проверки TypeScript и ESLint прошли. Код на VPS не развёрнут.

Новые скриншоты: накопленный Log Ingestion организации 25,183 GB, проекта `chestny_prigon` 23,78 GB (около 94%). Log Query — отдельная метрика, на скриншоте 32,056 / 2 500 GB; её нельзя складывать с Log Ingestion или приписывать worker. По накопленным значениям нельзя оценить результат вчерашнего отключения таймера.

В `list-timers` у `catalog-availability-monitor.timer` следующий запуск показан как `-`. Это не доказывает сбой: служба может ещё работать. Нужно проверить состояние таймера, службы, результат последнего запуска и журнал. Обновление курса pricing не является подтверждением проверки исходных цен Encar и доступности объявлений.

Панель Supabase, данные и production-конфигурация не изменялись. Анализ основан на предоставленных скриншотах и локальном коде; фактические unit-файлы, cron и процессы VPS не проверены.

## Что установлено

- На скриншоте GET `chestny_enrichment_runs` повторяется примерно каждые 10–11 секунд. Один такой непрерывный поток даёт около 7 850–8 640 запросов в сутки. Это лишь часть показанных 581,1 тысячи событий API Gateway: приписывать весь объём этому worker нельзя.
- В `scripts/radar/run-vps-enrichment.ts` чтение запуска находится в `main()` и выполняется один раз на старт процесса. Аналогичная проверка есть в `scripts/radar/run-report-retry.ts`. Ни один из этих файлов не опрашивает статус каждые 10 секунд внутри процесса.
- `deploy/chestny-enrichment.timer` и `deploy/chestny-report-retry.timer` задают интервал 5 минут. Службы имеют `Type=oneshot`, без `Restart=`. Локальная конфигурация не объясняет наблюдаемый интервал.
- До исправления завершённый или отменённый запуск вызывал ошибку с кодом 1. Внешний supervisor с перезапуском после ошибок мог создавать цикл запросов. Это гипотеза, требующая проверки работающего процесса.
- `telegram_posts` не встречается в этом репозитории и в проверенных соседних проектах `autoexport` и `autoexport-web`. Видимые пары запросов каждую минуту требуют отдельной атрибуции.
- Прежняя проверка завершения enrichment загружала все статусы очереди без пагинации. Ограничение количества строк ответа могло скрыть незавершённые элементы. При пустой партии финализация вообще пропускалась.

## Локальные исправления

1. Проверка живого приоритетного процесса Radar до обращения к Supabase. Проверка внутри обработки партии сохранена.
2. Проверка наличия `queued`/`leased` через `select id` с фильтром и `limit 1`. Ошибка запроса не считается пустой очередью.
3. Финализация запуска также после пустой партии. Обновление статуса ограничено `approved`/`running`, в том числе в report retry, чтобы не перезаписывать уже отменённый запуск.
4. Завершённые и отменённые запуски получают отдельный код выхода 78. В службах добавлены `SuccessExitStatus=78` и `RestartPreventExitStatus=78`; существующий код 75 report retry сохранён.

Код 78 предотвращает автоматический restart соответствующим systemd supervisor, но **не выключает timer**. Каждый следующий запуск timer всё ещё читает статус. Произвольный shell-цикл также должен отдельно обрабатывать код 78. Изменения unit-файлов начнут действовать только после их установки и `daemon-reload` на сервере; локальное редактирование этого не делает.
